# Project questions

Organizers can add per-event typed questions to the project submission form.
Participants answer them alongside the fixed project fields; organizers always see
the answers, and judges see them only when the per-event switch is on.

## Admin layout

The organizer console has two competition pages (organizer/owner only):

- **Submission Forms** (`/submission-forms?event=SLUG`): submission enablement and
  open/close dates, project questions, the **Judges can see question answers**
  switch, sponsor tracks, and the submitted-projects list. Project detail lives at
  `/submission-forms/projects/PROJECT_UUID?event=SLUG&projectsPage=N` and shows
  answers with their question labels.
- **Judging Management** (`/judging?event=SLUG`): judging end, general reviews per
  project, Start judging, judge roster, assignments, and results.

Both settings forms still save through `admin_save_competition_settings`. Each
server action reads the stored settings row and overwrites only its own fields, so
the two pages do not clobber each other's saved values.

## Behavior

- Each question has a label (1-300 characters), optional help text (up to 1,000),
  a required flag, and an answer type:

  | Type              | Answer stored in `projects.answers` | Settings                          |
  | ----------------- | ----------------------------------- | --------------------------------- |
  | `short_text`      | trimmed string                      | maximum length and unit           |
  | `long_text`       | trimmed string                      | maximum length and unit (default) |
  | `url`             | HTTP(S) URL string, up to 2,048     | none                              |
  | `single_choice`   | option id                           | 1-50 options                      |
  | `multiple_choice` | array of option ids                 | 1-50 options                      |
  | `file`            | `{path, name, size, type}`          | optional max size (MB, up to 10)  |

  Questions created before typed questions became `long_text` and keep their
  maximum length. Only text questions have a maximum length; only choice
  questions have options; only file questions have `validation`.

- Text limits count `characters` (1-10,000, the default) or `words` (1-1,500),
  stored in `project_questions.length_unit`. Every text answer is also capped at
  10,000 characters whatever the unit. Words are counted as described in
  [text-length-limits.md](text-length-limits.md). Existing questions are
  `characters`. Only text questions may use `words`.

- Choice options are `{id, label}` with stable uuid ids generated by the admin
  editor. Labels are trimmed, 1-200 characters, and unique ignoring case. Renaming
  an option keeps existing answers valid. Removing an option invalidates its id:
  on the next save the database drops unknown ids from the answer (the participant
  editor does the same when loading), so an optional question just loses that
  choice and a required one asks to be answered again. This never blocks a draft
  save for an unrelated edit; it only fails a complete save when the question is
  required and now empty, with the error on that question. Removed options move to
  `project_questions.archived_options`, which only the organizer RPCs read.
  Re-adding a label (trimmed, case-insensitive) that matches an active or archived
  option restores that option's id and unarchives it, in the same save or any
  later one; the editor and `admin_save_project_question` both apply this.
  Archived ids are not valid answers and are not rendered for judges or
  organizers, consistent with the participant's next save dropping them.
- Once any project has an answer for a question, its type cannot change (trigger
  on `project_questions`). The admin editor disables the type selector for
  answered questions and warns that removing options, lowering limits, or
  switching between characters and words can affect existing answers; to change type, archive the question and add a new one.
- Questions can be added, edited, reordered, and archived until **Start judging**;
  after that they are permanently locked (RPC check plus the shared freeze trigger).
- Archiving is a soft delete. Archived questions disappear from the participant
  form, judge view, and organizer project detail; only active questions are ever
  shown. A participant's next save drops answers to archived questions.
- Answers are validated per type in the database (`project_answer_errors`).
  Required questions apply on submit and on any save of an already-submitted
  project. Adding a required question later does not unsubmit existing projects;
  the requirement applies the next time a team member saves.
- Saving with an unknown or archived question id fails with a reload message, like
  other stale-form errors. Per-question errors are returned in the `PT422` detail
  map under `answers.<question_id>`.
- **Judges can see question answers** is one per-event switch, off by default. It
  can be changed at any time, including after judging starts or ends. Filtering
  happens in SQL: with the switch off, `judge_assignment` returns `answers: []`.

## File answers

- Private bucket `project-files`, PDF only, 10 MB. Object path
  `project_id/question_id/file_id.pdf`; the file answer must point at an existing
  object under its own project and question. Type and size come from the stored
  object's metadata (`mimetype`, `size`), never from the client, and the saved
  answer records those real values. An organizer cannot lower a file question's
  limit below the largest file already saved for it.
- Any team member (owner or collaborator) can upload or delete, and only while the
  project can be saved (submissions enabled and open, not closed, judging not
  started, project not withdrawn, the member still eligible). This mirrors
  `lock_participant_project`. Files
  referenced by saved answers cannot be deleted. After a successful save, the
  server action deletes (through the Storage API) files the previous answers
  referenced and the new ones do not. The editor deletes an upload that was never
  saved as soon as it is replaced or removed. An upload abandoned without saving
  (closed tab, failed request) stays in the bucket; there is no sweep job.
- Nobody downloads directly. The only read policy allows the Storage `sign`
  operations (plus members' own deletes), so every link is a 60-second signed
  URL created by a server action with the caller's session:
  - owner and collaborators: any file in their project;
  - organizers: any project file;
  - judges: only files that answer an active file question on one of their current
    assignments, and only while **Judges can see question answers** is on.

  The signing action takes only the path; `project_file_readable` in the storage
  policy is the authorization check.

## Database contract

Migration: `supabase/migrations/20261115000004_project_questions.sql`.

Migrations: `supabase/migrations/20261115000004_project_questions.sql`,
`20261116000001_typed_project_questions.sql`,
`20261116000002_project_files_storage.sql`,
`20261117000002_project_question_length_units.sql`.

```text
project_questions                       default-deny table, RLS on; type, length_unit, options, validation
event_competition_settings.judges_see_answers
projects.answers                        jsonb object: question id -> typed answer
storage bucket project-files            private, PDF, 10 MB

admin_project_questions(p_event_id)                      active questions by position, with answered flag
admin_save_project_question(p_event_id, p_label, p_help_text, p_required, p_max_length, p_question_id, p_type, p_options, p_validation, p_length_unit)
admin_archive_project_question(p_event_id, p_question_id)
admin_reorder_project_questions(p_event_id, p_question_ids)   every active id once
admin_set_judges_see_answers(p_event_id, p_value)
participant_save_project(p_project_id, p_content, p_answers, p_track_ids, p_submit, p_expected_updated_at)
project_file_writable(name) / project_file_deletable(name) / project_file_readable(name)
```

`participant_project_detail` adds `questions` (active, ordered, with `type`,
`options`, `validation`, `max_length`, `length_unit`) and the project's `answers`.
`judge_assignment` and `admin_submitted_project_detail` return
`answers: [{question_id, label, type, options, answer}]` where `answer` is the
stored JSON value or `null`; the organizer view ignores the switch. Clients render
choice ids as their current labels and ignore ids no longer in `options`.

## Verification

`supabase/tests/43_project_questions_test.sql` covers organizer-only access,
ordering, the judging freeze, the always-editable switch, answer validation, late
required questions, archived questions, and judge/organizer visibility.
`supabase/tests/45_typed_project_questions_test.sql` covers the type default,
configuration checks, per-type validation, removed options, the type lock, and
`project-files` policies for owner, collaborator, outsider, organizer, judge
(switch off and on), and after judging starts.
`supabase/tests/46_text_length_units_test.sql` covers word counting, unit
defaults, word caps, and character and word validation.

Manual check on a development sandbox: add a required and an optional question
of each type, submit a project as a participant, add another required question and confirm the
project stays submitted but the next save asks for it, then start judging and
toggle the switch while viewing a judge scorecard and opening an uploaded PDF.
